# 読みやすいコード

コメントを追加する前に、役割が分かる名前を付け、処理のまとまりが分かる関数へ分ける。
命名と関数分割を行ってもコードだけでは伝わらない判断理由、制約、不変条件をコメントで補う。

## コメントする対象

- 公開関数、型、定数の役割と、呼出側が守る条件
- 非自明なアルゴリズムやデータ変換を選んだ理由
- 処理中と処理後に維持する不変条件
- 並行処理における値や資源の所有権、ロック範囲、終了条件
- SQLiteを生成して検索先を切り替える条件と、旧DBを閉じる条件
- 入力検査が防ぐデータ破損、資源枯渇、曖昧な解釈
- 正規化で同一視する値と、区別したまま扱う値
- 互換性を維持するために残している処理と、維持する互換性
- 処理上限と、その上限が必要な理由
- Workaroundが必要になった原因と、削除できる条件

## コメントしない対象

- コードの処理をそのまま日本語で言い換えた説明
- 変数名や関数名だけで明らかな内容
- 将来必要になるかもしれないという理由だけで追加した設計
- Issue番号を確認しなければ意味が分からない説明
- 生成ファイルへの手書きコメント

既存コードへ一括でコメントを追加しない。
変更する処理とその周辺だけを読み、必要な箇所を改善する。

コメント率やコメント行数などの数値目標は設けない。
コメントの要否は、コードだけでは判断理由、制約、不変条件を維持できるかで決める。

## Goの例

SQLiteの切替では、操作の名前ではなく切替条件と資源の寿命を説明する。

```go
// よくない例：DBを切り替える。
old := current.Swap(next)
old.CloseWhenIdle()

// 良い例：検査済みのDBを先に公開し、切替中の検索が旧DBを参照できる状態を保つ。
old := current.Swap(next)
// 切替前に開始した検索の参照がなくなった後だけ旧DBを閉じる。
old.CloseWhenIdle()
```

入力検査では、検査が防ぐ問題を説明する。

```go
// よくない例：入力サイズを確認する。
body := http.MaxBytesReader(w, r.Body, maxArchiveSize)

// 良い例：圧縮後の上限を受信中に適用し、上限を超えた入力を保存処理へ渡さない。
body := http.MaxBytesReader(w, r.Body, maxArchiveSize)
```

正規化では、同一視する値と区別する値を明示する。

```go
// よくない例：検索語を正規化する。
normalized := normalizePath(query)

// 良い例：パスはUnicode NFKCと前後空白を同一視するが、大文字と小文字は区別する。
normalized := normalizePath(query)
```

処理上限では、値を置く理由と上限到達時の扱いを説明する。

```go
// よくない例：最大件数。
const maxTargets = 1_000

// 良い例：応答サイズを制限する。超過時は全件確認済みとせずtruncatedで通知する。
const maxTargets = 1_000
```

## レビュー

実装を変更した場合は、同じ変更で関連するコメントを更新する。
差分レビューでは、コメントが説明する理由、制約、不変条件と実装が一致していることを確認する。
実装から確認できない古い説明は残さず、現在の条件に合わせて修正または削除する。
