# 技術文書の書き方

このリポジトリの文書は、運用担当者と開発者が、設計の理由と具体的な動作を読み違えないことを優先します。
API名、JSONキー、列挙値、コマンド名は変更せず、その意味を自然な日本語で説明します。

## 文と段落

- 一文ごとに改行する。
- 段落は空行で区切る。
- 一つの段落では一つの論点だけを扱う。
- 段落の先頭で、扱う対象か直前との関係を示す。
- 「本節では」「次に説明する」など、文書の進行だけを述べる文を置かない。
- 根拠がある内容は具体的に書き、未確認の内容には不確実性を残す。
- 原因と結果を書く場合は、なぜそうなるのかを示す。

## 重複を避ける

- 一つの仕様は、最も関係の深い文書だけに詳しく記載する。
- 別の文書で同じ仕様に触れる場合は、要点を一文で示して正本へのリンクを置く。
- README、索引、概要文書には詳細な仕様や手順をコピーしない。
- コマンド手順は一か所にまとめ、他の文書では参照先だけを示す。
- 生成ファイルは正本と生成方法を明記し、同じ内容を手作業で複製しない。
- 図と本文が同じ情報を繰り返す場合は、図で分からない条件や例外だけを本文に書く。
- 同じ結論を言い換えて繰り返さない。
- 文書を分割するときは、各文書の責務が重ならないようにする。

## 図と表

| 表現 | 適した内容 | 避ける使い方 |
|---|---|---|
| Mermaidフロー図 | 処理の順序、分岐、データの流れ | 単純な箇条書きを図へ置き換えるだけの使用 |
| Mermaidシーケンス図 | 複数の主体間で行う要求と応答 | 一つの主体だけで完結する処理 |
| Mermaid状態遷移図 | 状態と遷移条件 | 状態を持たない処理手順 |
| Mermaid ER図 | テーブルと参照関係 | 列の詳しい制約や索引の説明 |
| 表 | 比較、対応関係、一覧、設定値 | 長い説明文や手順を一つのセルへ詰め込む |
| コードブロック | コマンド、JSON、HTTP、ログ、ファイル構成 | 通常の説明文 |

図や表は、文章より関係を短く正確に示せる場合に使います。
装飾のためには追加しません。

図の前後には、図が示す対象と、図だけでは分からない条件を記載します。
図中のラベルは短くし、詳しい条件は本文または表へ分けます。

同じ内容を図、表、本文の三か所へ書きません。
図が処理の流れを示す場合、本文は例外や判断規則だけを補います。
表が値の対応を示す場合、本文は表全体に共通する注意点だけを補います。

Mermaidは、GitHubと主要なMarkdown表示環境で解釈できる基本構文を使います。
独自テーマ、色指定、表示環境に依存する記法は使いません。

## コマンドの実行環境

- 実行するコマンドには、ホスト、Dev Container、CI、サービスコンテナなどの実行環境を明記する。
- 一つの手順で実行環境が変わる場合は、節またはコードブロックを分ける。
- Dev Containerで利用できないDocker操作を、開発コマンドとして並べない。
- コマンドが複数環境で動く場合も、このリポジトリで標準とする環境を示す。
- 概念を示すHTTPメッセージやJSON例には、実行環境を付けない。

## 実装方針の記載

- 将来の拡張を理由に、現在使わない仕組みを必須のように書かない。
- 抽象化や設定項目を追加する場合は、現在必要な利用例を示す。
- 厳密に検査する項目と、任意情報として受け入れる項目を区別する。
- 「柔軟に扱う」を、誤った値を黙って補正する意味で使わない。
- 性能対策は、測定前の案と採用済みの仕様を区別する。

## 文書の配置

- `docs/index.md`は文書の入口とし、詳細を記載しない。
- システムの仕様と設計判断は`docs/design/`へ置く。
- 開発、テスト、ビルドの手順は`docs/development/`へ置く。
- GitHubが表示するコントリビューション手順は、ルートの`CONTRIBUTING.md`へ置く。
- 運用担当者が直接参照する手順は`docs/`直下へ置く。
- 新しい分類は、同じ役割の文書が複数できた場合に限って追加する。
- 階層は深くしすぎず、`docs/`から2階層までを目安とする。

## 用語の選び方

初めて使う固有の概念は太字で示し、その場で意味を説明します。
定義した後は同じ語を使い、似た別語へ置き換えません。

分野で一般的な用語を優先します。
英語を直訳しただけの日本語や、意味を知らなければ読めない漢語は避けます。

次のような表現は、内容が分かる文へ置き換えます。

| 避ける表現 | 置き換え方 |
|---|---|
| 決定論的に処理する | 同じ入力には同じ結果を返す、定めた規則で処理する |
| HTTP契約、外部契約 | API仕様、公開する入出力形式 |
| 原子的に切り替える | 準備完了後に一度で切り替える |
| 実効依存遷移 | ファイルなどを介したジョブ間の依存関係 |
| 分析境界 | 処理を打ち切った地点 |
| 正規経路 | 採用する経路 |
| 探索フロンティア | 次に調べるノード、処理を打ち切った地点 |

コード上の識別子は翻訳しません。
`policyVersion`はそのまま記載し、本文では「順位付け規則の版」と説明します。

## 表記

- 日本語の並列には読点か箇条書きを使い、中黒を使わない。
- 見出しは、その節で扱う対象が分かる名詞句にする。
- 見出しへ二つ以上の論点を詰め込まない。
- コード、設定、ログ、JSON、HTTPメッセージはコードブロックで示す。
- 定義の一覧は、項目が少なければ「用語：説明」、比較が必要なら表を使う。
- 本文の流れを止める補足は、脚注か別節へ移す。
- 太字は用語の初出か、誤読を防ぐ箇所に限る。

## 説明の範囲

- 管理単位の親子関係と、実行上の依存関係を区別する。
- 定義に保存されたリミットと、現在の障害に対する対応期限を区別する。
- `declared`、`confirmed`、`inferred`、`candidate`の違いを保つ。
- 処理上限に達した結果を、全件を確認した結果として書かない。
- 例が仕様の一部だけを示す場合は、その範囲を明記する。
- API項目名を説明するときは、利用者が何を判断できるかを書く。

## 推敲

各文が、システムの状態、仕様、判断理由、手順のいずれかを新しく伝えているか確認します。
すでに別の文書で説明している内容は削除し、必要な場合だけリンクへ置き換えます。

長い断定文が続く場合は、比較は表、順序や分岐は図、具体的な形式はコードブロックへ分けます。
ただし、図や表へ置き換えるために必要な条件や例外を削ってはいけません。
