# 技術文書の書き方

BatchScopeの日本語技術文書には、`agent-skills` Pluginの`japanese-technical-writing`と、この文書のBatchScope固有規則を併せて適用します。
repository非依存の文書責務、主張の区別、用語一貫性、構成、図表、推敲は共有Skillで扱います。
この文書はBatchScope固有規則の正本です。
共有Skillとこの文書が競合する場合は、この文書を優先します。
共有できる一般原則はこの文書へ複製せず、`vnzzzz/agent-skills`側で更新します。

## 表記

- 一文ごとに改行する。
- 段落は空行で区切る。
- 日本語の並列には読点か箇条書きを使い、中黒を使わない。
- 見出しは、その節で扱う対象が分かる名詞句にする。
- 見出しへ二つ以上の論点を詰め込まない。
- 太字は用語の初出か、誤読を防ぐ箇所に限る。

Mermaidは、GitHubと主要なMarkdown表示環境で解釈できる基本構文を使います。
独自テーマ、色指定、表示環境に依存する記法は使いません。

## コマンドの実行環境

- 実行するコマンドには、ホスト、Dev Container、CI、サービスコンテナなどの実行環境を明記する。
- 一つの手順で実行環境が変わる場合は、節またはコードブロックを分ける。
- Dev Containerで利用できないDocker操作を、開発コマンドとして並べない。
- コマンドが複数環境で動く場合も、このリポジトリで標準とする環境を示す。
- 概念を示すHTTPメッセージやJSON例には、実行環境を付けない。

## 実装方針の記載

- 将来の拡張を理由に、現在使わない仕組みを必須のように書かない。
- 抽象化や設定項目を追加する場合は、現在必要な利用例を示す。
- 厳密に検査する項目と、任意情報として受け入れる項目を区別する。
- 「柔軟に扱う」を、誤った値を黙って補正する意味で使わない。
- 性能対策は、測定前の案と採用済みの仕様を区別する。

## 文書の配置

- `docs/index.md`は文書の入口とし、詳細を記載しない。
- システムの仕様と設計判断は`docs/design/`へ置く。
- 開発、テスト、ビルドの手順は`docs/development/`へ置く。
- GitHubが表示するコントリビューション手順は、ルートの`CONTRIBUTING.md`へ置く。
- 運用担当者が直接参照する手順は`docs/`直下へ置く。
- 新しい分類は、同じ役割の文書が複数できた場合に限って追加する。
- 階層は深くしすぎず、`docs/`から2階層までを目安とする。

## BatchScopeの用語

初めて使うBatchScope固有の概念は太字で示し、その場で意味を説明します。
定義した後は同じ語を使い、似た別語へ置き換えません。

次の表現は、BatchScopeの文書では右欄の具体的な説明へ置き換えます。

| 避ける表現 | 置き換え方 |
|---|---|
| 決定論的に処理する | 同じ入力には同じ結果を返す、定めた規則で処理する |
| HTTP契約、外部契約 | API仕様、公開する入出力形式 |
| 原子的に切り替える | 準備完了後に一度で切り替える |
| 実効依存遷移 | ファイルなどを介したジョブ間の依存関係 |
| 分析境界 | 処理を打ち切った地点 |
| 正規経路 | 採用する経路 |
| 探索フロンティア | 次に調べるノード、処理を打ち切った地点 |

コード上の識別子は翻訳しません。
`limitOwner`はそのまま記載し、本文では「リミットの設定先ジョブ」と説明します。

## BatchScope固有の説明範囲

- 管理単位の親子関係と、実行上の依存関係を区別する。
- 定義に保存されたリミットと、現在の障害に対する対応期限を区別する。
- `declared`、`confirmed`、`inferred`、`candidate`の違いを保つ。
- 処理上限に達した結果を、全件を確認した結果として書かない。
- API項目名を説明するときは、利用者が何を判断できるかを書く。

## 規則の更新

repository非依存の日本語技術文書原則を変更する場合は、`vnzzzz/agent-skills`の`japanese-technical-writing`を更新します。
BatchScope固有の用語、表記、文書配置、実行環境、説明範囲を変更する場合は、この文書を更新します。
共有Skillの文章をこの文書へコピーして二重管理しません。
