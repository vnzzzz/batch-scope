# 取込と静的解析の性能測定結果

- 測定日：2026-08-10
- 測定対象：取込、静的解析、SQLite接続方式の性能測定用作業ツリー
- 基準コミット：`034edb2f0f3cee661007392ecb60ff52e6a99f96`

上記の測定日、測定対象、基準コミットは、取込、静的解析、SQLite接続方式の測定だけに適用します。
リミット設定数とSCCサイズの境界測定には適用しません。

この文書は、初期対応規模と検索方式を判断するための測定条件と結果を記録します。

## 測定コマンド

実行環境：Dev Container

```bash
GOCACHE=/tmp/batchscope-go-cache \
  go run ./cmd/perf-measure -profile small -runs 3 \
  > /tmp/batchscope-perf-small-review1.json

GOCACHE=/tmp/batchscope-go-cache \
  make perf-growth PERF_GROWTH_RUNS=2

GOCACHE=/tmp/batchscope-go-cache \
  go run ./cmd/perf-measure -mode import -profile medium -runs 2 \
  > /tmp/batchscope-perf-medium-import-review1.json

GOCACHE=/tmp/batchscope-go-cache \
  go run ./cmd/perf-measure -mode concurrent -profile small \
  -runs 2 -concurrencies 1,2,4,8 \
  > /tmp/batchscope-perf-concurrent-review1.json

GOCACHE=/tmp/batchscope-go-cache \
  PERF_CONNECTION_COMPARISON_RUNS=5 \
  make perf-connection-comparison \
  > /tmp/batchscope-perf-connection-comparison-review2.json
```

Smallは3反復、中間規模とMedium取込は2反復です。
並行負荷は各並行度を2ラウンド実行しました。
接続方式の比較は各方式と各並行度を5ラウンド実行しました。

`cold`は`PRAGMA shrink_memory`でSQLite接続のページキャッシュを解放した状態、`warm`は直前の`cold`から同じ接続を再利用した状態です。
OSのページキャッシュはどちらも保持しており、ストレージを含む完全なcold startではありません。

## Medium

Mediumの入力は100,000ノード、300,000 relationで、アーカイブのSHA-256は`b14d436dafe9822cbec7f63c3ebd93d867fa4e4ff79a215f29e2b79f9b613ea3`です。
取込は2反復とも完走しました。

| 指標 | 値 |
|---|---:|
| 取込全体の中央値 | 22.128 s |
| 受信の中央値 | 1.438 ms |
| 展開の中央値 | 3.978 s |
| 検査の中央値 | 4.990 s |
| SQLite登録の中央値 | 9.151 s |
| 完了処理の中央値 | 3.992 s |
| Heap増分の最大 | 77,198,920 bytes（73.62 MiB） |
| RSS増分の最大 | 78,737,408 bytes（75.09 MiB） |
| 一時ディスクの最大 | 114,511,963 bytes（109.21 MiB） |
| SQLiteサイズ | 92,311,552 bytes（88.04 MiB） |

Mediumの静的解析は、同じDev Containerで過去に二回試行し、どちらもOOM killerに終了され、JSONを出力するまで完走しませんでした。
今回の再測定では環境のメモリ不足が既知であるため、取込だけを測定しました。

Mediumの必要メモリは、中間規模のrelation数と最大Heapまたは最大RSSを両対数へ変換し、4点の最小二乗直線を300,000 relationまで外挿すると、Heap 6.57 GiB、RSS 6.56 GiBです。
100,000 relationから200,000 relationの二点だけを使って外挿すると、Heap 7.40 GiB、RSS 7.54 GiBです。
これらは未完走のMediumを直接測った値ではなく、実測した中間規模から求めた**推定値**です。

推定した最大RSSは6.6 GiBから7.5 GiBであり、失敗時の利用可能メモリ約3.3 GiBを3.3 GiBから4.2 GiB上回ります。
総メモリ7.65 GiBに対してもOSとほかのプロセスの分を残せないため、OOMで完走しない結果と整合します。
Mediumの完全な解析測定には、少なくとも8 GiBの利用可能メモリを持つ環境を目安とします。

## Scale

Scaleの取込と静的解析は測定していません。
Mediumの解析が完走しない環境で1,000,000ノード、3,000,000 relationを開始すると、結果を得ずに資源を消費するためです。
MediumからScaleまでを一つの外挿で推定するには規模差が大きいため、Scaleの必要メモリも推定していません。

## 並行負荷

Smallの`NET-TARGET`を同じSQLiteへ接続して測定しました。
レイテンシは全検索の分布、スループット、接続待ち回数、接続待ち時間は2ラウンドの分布です。

| 並行度 | レイテンシ最小 | 中央値 | p95 | 最大 | スループット中央値 | 接続待ち回数中央値 | 接続待ち時間中央値 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 436.823 ms | 447.585 ms | 458.347 ms | 458.347 ms | 2.24 search/s | 0 | 0 s |
| 2 | 602.618 ms | 615.481 ms | 629.134 ms | 629.134 ms | 3.24 search/s | 520 | 323.647 ms |
| 4 | 1.005 s | 1.036 s | 1.062 s | 1.062 s | 3.80 search/s | 1,029 | 2.056 s |
| 8 | 1.761 s | 1.986 s | 2.215 s | 2.215 s | 3.88 search/s | 2,075 | 10.177 s |

全ラウンドで`MaxOpenConnections`は1でした。
並行度2から接続待ちが発生し、並行度4から8ではスループットが約3.8 search/sでほぼ頭打ちとなり、中央値レイテンシと接続待ち時間が増えました。
単一SQLite接続がSQL実行を直列化している観測結果です。
接続方式を変更するかは、この結果だけでは決めません。

## SQLite接続方式の比較

単一接続の並行度4から8でスループットが約3.8 search/sのまま頭打ちとなり、接続待ち時間だけが増えたため、接続方式の比較条件を満たしたと判断しました。
比較には、[並行負荷](#並行負荷)の測定と同じ最大1接続の方式と、最大接続数を並行度と同じ値にした複数読み取り接続を含めました。

比較では、Smallの同じアーカイブを一回だけ取り込み、作成したSQLiteを測定用の世代固有パスへ複製しました。
アーカイブのSHA-256はSmall測定と同じ`60b332fc50901cacdf5f95eb5560bcc540f58f151871afab9ce53750be08cb71`です。
製品の`store`を閉じた後、両方式を同じSQLiteファイルへ読み取り専用かつ不変ファイルとして接続し、最大接続数以外の条件を揃えました。

単一接続の並行負荷測定時の`store`は`current.db`のパスを次世代でも再利用し、`foreign_keys`が接続単位の設定であるため、接続を1本に固定して期限なしで保持していました。
比較試作では、世代ごとに再利用しないSQLiteファイルパスを割り当てることで、旧ハンドルの再接続先が次世代へ変わることを防ぎました。
さらに、DSNで`foreign_keys=on`と`query_only=on`を指定し、接続プールに作成した全接続から両方のPRAGMAが有効であることを測定開始前に確認しました。

各ラウンドの前に対象の接続プールにある全接続で`PRAGMA shrink_memory`を実行し、OSのページキャッシュは保持しました。
同じプロセス内で二方式を連続実行し、どちらを先に測るかをラウンドと並行度ごとに交互にしました。
レイテンシは並行度と5ラウンドを掛けた全検索の分布、スループットと接続待ちは5ラウンドの分布です。

| 方式 | 並行度 | レイテンシ最小 | 中央値 | p95 | 最大 | スループット中央値 | 接続待ち回数中央値 | 接続待ち時間中央値 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 単一接続 | 1 | 411.932 ms | 433.456 ms | 444.226 ms | 444.226 ms | 2.31 search/s | 0 | 0 ms |
| 複数読み取り接続 | 1 | 414.537 ms | 435.902 ms | 457.830 ms | 457.830 ms | 2.29 search/s | 0 | 0 ms |
| 単一接続 | 2 | 593.563 ms | 613.257 ms | 662.575 ms | 662.575 ms | 3.26 search/s | 520 | 333.315 ms |
| 複数読み取り接続 | 2 | 484.445 ms | 496.098 ms | 514.851 ms | 514.851 ms | 4.02 search/s | 0 | 0 ms |
| 単一接続 | 4 | 941.027 ms | 1,007.532 ms | 1,107.704 ms | 1,113.983 ms | 3.95 search/s | 1,028 | 1,969.956 ms |
| 複数読み取り接続 | 4 | 720.433 ms | 775.805 ms | 839.499 ms | 840.481 ms | 5.09 search/s | 0 | 0 ms |
| 単一接続 | 8 | 2,145.372 ms | 2,254.609 ms | 2,393.238 ms | 2,417.140 ms | 3.50 search/s | 2,083 | 12,190.646 ms |
| 複数読み取り接続 | 8 | 1,295.930 ms | 1,514.944 ms | 1,692.664 ms | 1,728.169 ms | 5.12 search/s | 0 | 0 ms |

複数読み取り接続の中央値を単一接続と比較した差は次のとおりです。
正のスループット差は増加、負のレイテンシ差は短縮を示します。

| 並行度 | 中央値レイテンシの差 | スループット中央値の差 |
|---:|---:|---:|
| 1 | +0.6% | -0.6% |
| 2 | -19.1% | +23.5% |
| 4 | -23.0% | +29.0% |
| 8 | -32.8% | +46.4% |

複数読み取り接続は並行度2、4、8で`database/sql`の接続待ちを発生させず、単一接続より中央値レイテンシを短縮し、スループット中央値を増やしました。
並行度4から8のスループットは5.09 search/sから5.12 search/sであり、接続待ち以外のCPU、メモリ割当て、`Build`などが次の制約になった可能性があります。
これは測定結果からの推測であり、要因別の測定は行っていません。

複数読み取り接続を採用する場合は、接続ごとのページキャッシュとファイルハンドル、および切替中に保持する新旧世代の資源を合わせて見積もる必要があります。
採用後の世代寿命と接続設定は[SQLiteの構成](../design/storage.md)を正本とします。

不変オンメモリ検索構造は今回の比較へ含めませんでした。
観測された兆候がSQLite接続待ちだったため、同じSQLiteと検索実装のまま接続数だけを変える最小限の比較を優先しました。
オンメモリ方式は保存方式と検索方式も変わり、構築時間、世代切替時のメモリ重複、索引の表現を別に測る必要があります。

この比較だけでは接続方式を製品へ採用せず、対応規模、接続方式、SQLite方式を継続するかを判断する材料としました。
確定した判断は末尾の[判断先](#判断先)に記載します。

## リミット設定数とSCCサイズの境界

この境界測定は、冒頭のメタ情報が適用される測定とは別の作業ツリーで実施しました。
Dev Containerで`go test`を介して取込後の静的解析を実行しました。
内部処理合計は後続探索、リミット抽出、経路ツリー生成の合計であり、HTTP層のDTO組立てとJSON化を含みません。
`alloc`は解析前後の`runtime.MemStats.TotalAlloc`の増分、`heapInUse`は`runtime.MemStats.HeapInuse`の増分です。

リミット設定数の測定では、ノード数とrelation数を初期対応規模の上限に固定しました。

| リミット設定数 | 内部処理合計 | 経路ツリー生成 | alloc | heapInUse | 経路ツリー |
|---:|---:|---:|---:|---:|---:|
| 53 | 1.036 s | 742 ms | 1,113.2 MiB | 836.3 MiB | 25,001 |
| 500 | 1.087 s | 792 ms | 1,114.2 MiB | 727.4 MiB | 25,001 |
| 1,000 | 1.021 s | 719 ms | 1,115.2 MiB | 833.6 MiB | 25,001 |
| 2,000 | 1.025 s | 723 ms | 1,117.6 MiB | 759.4 MiB | 25,001 |
| 5,000 | 1.128 s | 799 ms | 1,125.3 MiB | 844.0 MiB | 25,001 |

すべての条件で宣言したリミットを全件返しました。
リミット設定数を53件から5,000件へ増やしたときの内部処理合計の増加は約9%であり、リミット設定数は処理時間の支配要因ではありませんでした。

| 2,500 | 535 ms | 491 ms | 78.6 MiB | 5,003 |
| 3,000 | 717 ms | 670 ms | 105.7 MiB | 6,003 |

## 判断先

この測定結果に基づき、初期対応規模を10,000ノード、25,000 relation、5,000リミット設定、ジョブネット階層深さ64、想定同時検索数4と確定しました。
検索には索引付きSQLiteを継続し、不変オンメモリ検索構造を導入せず、最大4の読み取り接続を使用します。
判断と根拠は[設計判断](../design/decisions.md#対応規模と検索方式)に記録します。

公開HTTPの完全一致検索は[完全一致検索のHTTP性能測定結果](target-search-performance.md)で測定済みです。
後続リミット解析の公開HTTPは測定済みです。
条件と結果は[後続リミット取得のHTTP性能測定結果](limit-analysis-performance.md)を参照してください。
