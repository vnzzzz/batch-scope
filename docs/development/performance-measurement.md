## 測定コマンド

実行環境：Dev Container

次のコマンドは、冒頭の基準コミットを起点とした当時の性能測定用作業ツリーで実行した記録です。

```bash

GOCACHE=/tmp/batchscope-go-cache \
```

Smallは3反復、中間規模とMedium取込は2反復です。
並行負荷は各並行度を2ラウンド実行しました。

`cold`は`PRAGMA shrink_memory`でSQLite接続のページキャッシュを解放した状態、`warm`は直前の`cold`から同じ接続を再利用した状態です。
OSのページキャッシュはどちらも保持しており、ストレージを含む完全なcold startではありません。

| 一時ディスクの最大 | 114,511,963 bytes（109.21 MiB） |

Mediumの静的解析は、同じDev Containerで過去に二回試行し、どちらもOOM killerに終了され、JSONを出力するまで完走しませんでした。
今回の再測定では環境のメモリ不足が既知であるため、取込だけを測定しました。

Mediumの必要メモリは、中間規模のrelation数と最大Heapまたは最大RSSを両対数へ変換し、4点の最小二乗直線を300,000 relationまで外挿すると、Heap 6.57 GiB、RSS 6.56 GiBです。
100,000 relationから200,000 relationの二点だけを使って外挿すると、Heap 7.40 GiB、RSS 7.54 GiBです。
これらは未完走のMediumを直接測った値ではなく、実測した中間規模から求めた**推定値**です。

推定した最大RSSは6.6 GiBから7.5 GiBであり、失敗時の利用可能メモリ約3.3 GiBを3.3 GiBから4.2 GiB上回ります。
総メモリ7.65 GiBに対してもOSとほかのプロセスの分を残せないため、OOMで完走しない結果と整合します。
Mediumの完全な解析測定には、少なくとも8 GiBの利用可能メモリを持つ環境を目安とします。

## Scale

Scaleの取込と静的解析は測定していません。

## SQLite接続方式の比較

単一接続の並行度4から8でスループットが約3.8 search/sのまま頭打ちとなり、接続待ち時間だけが増えたため、接続方式の比較条件を満たしたと判断しました。
比較には、[並行負荷](#並行負荷)の測定と同じ最大1接続の方式と、最大接続数を並行度と同じ値にした複数読み取り接続を含めました。

比較では、Smallの同じアーカイブを一回だけ取り込み、作成したSQLiteを測定用の世代固有パスへ複製しました。
アーカイブのSHA-256はSmall測定と同じ`60b332fc50901cacdf5f95eb5560bcc540f58f151871afab9ce53750be08cb71`です。
製品の`store`を閉じた後、両方式を同じSQLiteファイルへ読み取り専用かつ不変ファイルとして接続し、最大接続数以外の条件を揃えました。

単一接続の並行負荷測定時の`store`は`current.db`のパスを次世代でも再利用し、`foreign_keys`が接続単位の設定であるため、接続を1本に固定して期限なしで保持していました。
比較試作では、世代ごとに再利用しないSQLiteファイルパスを割り当てることで、旧ハンドルの再接続先が次世代へ変わることを防ぎました。
さらに、DSNで`foreign_keys=on`と`query_only=on`を指定し、接続プールに作成した全接続から両方のPRAGMAが有効であることを測定開始前に確認しました。

各ラウンドの前に対象の接続プールにある全接続で`PRAGMA shrink_memory`を実行し、OSのページキャッシュは保持しました。
同じプロセス内で二方式を連続実行し、どちらを先に測るかをラウンドと並行度ごとに交互にしました。
レイテンシは並行度と5ラウンドを掛けた全検索の分布、スループットと接続待ちは5ラウンドの分布です。

| 方式 | 並行度 | レイテンシ最小 | 中央値 | p95 | 最大 | スループット中央値 | 接続待ち回数中央値 | 接続待ち時間中央値 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 単一接続 | 1 | 411.932 ms | 433.456 ms | 444.226 ms | 444.226 ms | 2.31 search/s | 0 | 0 ms |
| 複数読み取り接続 | 1 | 414.537 ms | 435.902 ms | 457.830 ms | 457.830 ms | 2.29 search/s | 0 | 0 ms |
| 単一接続 | 2 | 593.563 ms | 613.257 ms | 662.575 ms | 662.575 ms | 3.26 search/s | 520 | 333.315 ms |
| 複数読み取り接続 | 2 | 484.445 ms | 496.098 ms | 514.851 ms | 514.851 ms | 4.02 search/s | 0 | 0 ms |
| 単一接続 | 4 | 941.027 ms | 1,007.532 ms | 1,107.704 ms | 1,113.983 ms | 3.95 search/s | 1,028 | 1,969.956 ms |
| 複数読み取り接続 | 4 | 720.433 ms | 775.805 ms | 839.499 ms | 840.481 ms | 5.09 search/s | 0 | 0 ms |

複数読み取り接続の中央値を単一接続と比較した差は次のとおりです。
正のスループット差は増加、負のレイテンシ差は短縮を示します。

| 並行度 | 中央値レイテンシの差 | スループット中央値の差 |
|---:|---:|---:|
| 1 | +0.6% | -0.6% |
| 2 | -19.1% | +23.5% |
| 4 | -23.0% | +29.0% |
| 8 | -32.8% | +46.4% |

複数読み取り接続は並行度2、4、8で`database/sql`の接続待ちを発生させず、単一接続より中央値レイテンシを短縮し、スループット中央値を増やしました。
並行度4から8のスループットは5.09 search/sから5.12 search/sであり、接続待ち以外のCPU、メモリ割当て、`Build`などが次の制約になった可能性があります。
これは測定結果からの推測であり、要因別の測定は行っていません。

複数読み取り接続を採用する場合は、接続ごとのページキャッシュとファイルハンドル、および切替中に保持する新旧世代の資源を合わせて見積もる必要があります。
採用後の世代寿命と接続設定は[SQLiteの構成](../design/storage.md)を正本とします。

不変オンメモリ検索構造は今回の比較へ含めませんでした。
観測された兆候がSQLite接続待ちだったため、同じSQLiteと検索実装のまま接続数だけを変える最小限の比較を優先しました。
オンメモリ方式は保存方式と検索方式も変わり、構築時間、世代切替時のメモリ重複、索引の表現を別に測る必要があります。

この比較だけでは接続方式を製品へ採用せず、対応規模、接続方式、SQLite方式を継続するかを判断する材料としました。
確定した判断は末尾の[判断先](#判断先)に記載します。

## リミット設定数とSCCサイズの境界

この境界測定の値を初めて記録したrevisionは`03d8855ada7e82666ef7cc3d6283afb68efea730`です。
このrevisionの作業ツリーで、Dev Containerから取込後の後続探索、リミット抽出、経路ツリー生成を計測しました。
内部処理合計は三処理の合計であり、HTTP層のDTO組立てとJSON化を含みません。
`alloc`は解析前後の`runtime.MemStats.TotalAlloc`の増分、`heapInUse`は`runtime.MemStats.HeapInuse`の増分です。

リミット設定数は`CapacityBoundary(10_000, 25_000, limitCount)`を使い、`limitCount`を53、500、1,000、2,000、5,000と変えて測定しました。
SCCサイズは`DenseSCC(size, size)`を使い、`size`を1,000、2,000、2,500、3,000、4,000、6,000、8,000、9,990と変えて測定しました。
`CapacityBoundary`と`DenseSCC`の生成規則は現在も`internal/testsupport/graphgen`で管理しています。

当時の時間と`runtime.MemStats`を記録した一時的な計測コードはrepositoryへcommitされていません。
そのため、下表の各値を現在のrepositoryから同じコマンドで再生成できるとは扱いません。
当時の実行コマンドを推測して記載せず、revision、入力条件、残っている測定結果だけを履歴として保持します。

現在の通常suiteでは、Smallの全パイプラインと3,000ノードSCCの完遂、SCC上限超過の取込拒否を軽量な回帰境界として確認します。
5,000リミットと40万ノード級の全パイプラインは、`go test -race ./...`へ重複して持ち込まず、Issue #52で追加した`operational` profileの専用測定で確認します。

```bash
GOCACHE=/tmp/batchscope-go-cache \
  go test \
  -run 'TestScalePipelineSmall|TestSCCCapacityBoundaryPipeline' \
  -count=1 -v ./internal/importer

go run ./cmd/perf-measure -profile operational -runs 2
```

これらは採用済み境界の完遂可否を確認する入口であり、下表に残す過去の時間、`alloc`、`heapInUse`を再生成するコマンドではありません。
`MaxSnapshotLimits`または`MaxSCCNodes`を性能根拠で変更する場合は、候補値を測定できる専用の再現可能な性能測定手順を先に用意し、測定revision、generator引数、実行コマンド、指標を新しい判断根拠と同じ変更で記録します。

## 判断先

### `pathtree`メモリ削減の比較

400k対応の上限定数だけを変更した状態で、100,000ノード / 300,000 relationのMedium形状を再測定すると、検索中RSS増分が約6.50 GiBに達しました。
主因は、`pathtree`が各候補経路へrootからのnode ID列とrelation ID列を重複保持していたことです。

経路を`previous`参照のDAGとして保持し、辞書順比較時だけscratchへ展開する方式へ変更した後の同一形状は次のとおりです。

| 指標 | 変更前 | 変更後 |
|---|---:|---:|
| 内部解析 p95 | 23.72 s | 25.94 s |
| `Build` p95 | 19.88 s | 22.35 s |
| Heap増分 p95 | 約5.64 GiB | 約527 MiB |
| RSS増分 p95 | 約6.50 GiB | 約588 MiB |

CPU時間は約1割増えましたが、Heap/RSSを約90%削減しました。
検索結果、代表経路規則、リミット、`uncoveredRoutes`は切り詰めていません。

### 判定

400,000ノード / 300,000 relationを取込時の対応規模へ引き上げます。
代表targetは並行度4でもp95 1秒目標へ十分な余力があります。
一方、snapshot全体へ到達する最悪targetや高密度relation形状を1秒以内に処理することは性能目標に含めず、完全解析を優先します。
旧10秒deadlineでは測定済みの正常な全件解析を途中で失敗させるため、異常時deadlineを60秒へ変更します。

Operational、Mediumのような大規模profileは通常の`make verify`へ含めません。
通常suiteでは同じfailure modeを小さいfixtureで検査し、対応規模の実測はこの専用手順で再現します。
